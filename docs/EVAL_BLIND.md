# 블라인드 평가

`backend/eval/dataset.jsonl`(회귀 평가셋 135개)은 탐지기를 만든 사람이 함께 작성해서, 점수가 높게 나오는 게 당연하다. 일반화 성능을 보려고 **탐지기 코드와 기존 평가셋을 보지 않은 작성자**(별도 LLM 에이전트)에게 평가셋을 따로 맡겼다.

## 데이터

- 160개 케이스: 민감값이 있는 95개, 없는 65개. 정답 값 205개.
- 23개 장르: Slack·카카오톡 대화, CS·Jira 티켓, 회의록, 서버·앱 로그, `.env`·YAML·JSON·properties 설정, Python·JS·Java·SQL·셸 코드, CSV, 인사·회계·고객 문서, 오류 리포트.
- 민감값이 없는 케이스에는 타임스탬프, 버전, 주문·송장 번호, ISBN, 해시, UUID, 공인·잘못된 IP, placeholder, AWS 문서 예제 키, 환경변수 참조, 마스킹된 값을 섞었다.
- 서비스 토큰은 GitHub push protection에 막히지 않도록 `{{gen:...}}` 템플릿으로 쓰고 평가 시점에 생성한다.

## 절차

1. 케이스 id의 SHA-256 해시로 **dev 83개 / test 77개**를 나눴다.
2. dev 결과만 보고 실패 원인을 분석해 탐지기를 고쳤다.
3. test는 수정이 끝난 뒤 **한 번만** 실행했다. 이 첫 실행이 공식 수치다.

결과를 보기 전에 정한 채점 규칙: 다른 정답 값 안에 들어 있는 값(예: DB URL 안의 IP·비밀번호)은 바깥 값 하나로 합쳐 가리는 설계라 span 채점에서 빼고, 출력에 남는지는 유출 검사로 따로 본다. dev를 처음 채점할 때는 이 규칙을 라벨 단위로만 적용해서 케이스 1개(blind_051)가 잘못 채점됐고, 이후 평가기에서 등장 위치 단위로 바로잡았다.

## 결과

| 실행 | span precision | span recall | span F1 | 유출 케이스 | 케이스 통과 |
|---|---:|---:|---:|---:|---:|
| v4.2(원본) · test | 0.583 | 0.625 | 0.603 | 17 / 77 | 51 / 77 |
| v5 · dev 수정 전 | 0.967 | 0.889 | 0.926 | 5 / 83 | 73 / 83 |
| v5 · dev 수정 후 | 1.000 | 1.000 | 1.000 | 0 / 83 | 79 / 83 |
| **v5 · test 첫 실행(공식)** | **0.990** | **0.990** | **0.990** | **1 / 77** | **74 / 77** |

원본 v4.2는 한국 개인정보 탐지기가 없고(주민·사업자번호·계좌 recall 0), 전화번호 정규식이 타임스탬프 같은 숫자를 잡아 오탐이 36건이었다.

실행 기록: [`eval-runs/`](eval-runs/) (0: v4.2 기준선, 1: dev 수정 전, 2: test 첫 실행, 3: dev 수정 후, 4: test 재실행)

## dev에서 찾아 고친 것

| 실패 | 수정(일반 규칙) |
|---|---|
| "국민 817201-01-224513 **계좌** 맞지?" — 키워드가 번호 뒤에 옴 | 바로 앞 은행 약칭, 바로 뒤 키워드(구분자 전까지)도 문맥으로 인정 |
| CSV 헤더 `카드번호`, SQL `INSERT ... (name, brn, ...)` 열 이름 | 표의 열 이름을 문맥으로 사용(텍스트당 한 번 분석해 캐시) |
| 실제 키에 `ExAmPLE`이 섞여 예제 값으로 오인 | placeholder 단어는 사람이 쓰는 형태(소문자·대문자·첫 글자 대문자)만 인정 |
| `Bearer sk-proj-…`가 Bearer(마스킹)로 분류돼 차단되지 않음 | 서비스별 형식이 확인된 키를 Bearer보다 우선 |
| `jdbc:oracle:thin:@host`, `cfg.setPassword("…")` | Oracle thin 형식, setter·builder 호출 인자 탐지(`get…` 호출은 제외) |
| `"pass": "…"`, `CLIENT_SECRET = "…"` | `pass`/`pw`로 끝나는 키, client secret을 API 자격증명으로 분류 |
| 코드가 헤더 문자열만 언급했는데 아래 코드 전체를 가림 | END가 없을 때는 다음 줄이 base64일 때만 끝까지 가림 |

## test에서 남은 실패(첫 실행 이후 분석)

| 케이스 | 원인 | 조치 |
|---|---|---|
| blind_076 (유출) | YAML 키 형태 `bearer: <token>` | 설정 키 형태 Bearer 탐지 추가 — 이후 test는 블라인드가 아님 |

## 알려진 한계

- **키워드 규칙 오탐**: "admin", "prod", "corp", "secret" 같은 단어가 있으면 내용과 무관하게 줄 전체를 가린다. 민감값이 없는 케이스 중 dev 4/38, test 2/27이 이 때문에 실패했다. 규칙을 "경고만 하고 가리지 않기"로 바꾸면 오탐은 사라지지만, Gemma가 꺼져 있을 때 문맥상 위험한 줄을 가리던 보호가 약해진다(회귀 평가셋 6개가 이 동작을 기대).
- 평가셋 작성자는 LLM 하나라 라벨 기준이 한 사람의 판단이다. test 77개는 표본이 작아 F1 0.990의 신뢰구간이 넓다.
- Gemma(LLM) 경로와 Gitleaks는 이번 평가에서 꺼져 있었다.
